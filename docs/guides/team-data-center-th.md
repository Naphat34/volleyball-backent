# ศูนย์ข้อมูลทีม

## การใช้งาน

เจ้าหน้าที่ทีมเปิด **ศูนย์ข้อมูลทีม** เพื่อจัดการทะเบียนนักกีฬาและเจ้าหน้าที่ของทีมตนเอง ค้นหา กรองข้อมูลที่ต้องตรวจ หรือพักใช้งานแทนการลบ ข้อมูลทะเบียนกับรายชื่อรายการเป็นคนละส่วน การเพิ่มคนในทะเบียนไม่เลือกเข้ารายการให้อัตโนมัติ

ที่ **รายชื่อรายการ** เลือกนักกีฬาอย่างน้อย 6 คน กำหนดหมายเลขเสื้อ ตำแหน่ง กัปตัน Libero และเจ้าหน้าที่ประจำรายการ บันทึกร่างได้ก่อน แล้วตรวจและยืนยัน ระบบตรวจคุณสมบัติและจำนวนสูงสุดของรายการ ฝั่งบันทึกคะแนน/สถิติจะตรวจการยืนยันก่อนเริ่มบันทึกการแข่งขัน

รายชื่อที่มีอยู่ก่อนอัปเดตจะคงเป็นรายชื่อที่ยืนยันแล้ว หากพบข้อมูลผิดเงื่อนไขต้องตรวจแก้ก่อนเริ่ม รายชื่อใหม่ต้องเลือกและยืนยันเอง การแก้ข้อมูลที่กระทบคุณสมบัติของรายชื่อที่ยังไม่ล็อกจะให้ตรวจยืนยันอีกครั้ง

รายชื่อที่ล็อกแล้วส่งคำขอพร้อมเหตุผล โดยยังไม่เปลี่ยนรายชื่อจริง Super Admin เปิด `/access-center?view=roster_requests` เปรียบเทียบรายชื่อก่อนและหลัง แล้วอนุมัติหรือปฏิเสธพร้อมเหตุผล ผู้ดูแลส่วน Scorer/VIMS ไม่มีสิทธิ์อนุมัติ หากข้อมูลเปลี่ยนหลังส่งคำขอ ระบบป้องกันการอนุมัติข้อมูลเก่า ให้ปฏิเสธและส่งคำขอใหม่

Scorer ยังคงเพิ่มนักกีฬาและเจ้าหน้าที่ผ่าน Match settings เข้าทะเบียน รายการ และแมตช์ได้ทันทีตามสิทธิ์เดิม โดยไม่ยกเลิกการยืนยันรายชื่อเดิม แมตช์ที่เริ่มหรือจบแล้วเก็บรายชื่อย้อนหลังไว้ การอนุมัติรายชื่อรายการไม่เปลี่ยนคะแนนหรือสถิติเก่า

นำเข้า Excel จะเห็นผลตรวจแต่ละแถว เลือกนำเข้าเฉพาะแถวที่ผ่านได้ แถวผิดหรือไม่ได้เลือกยังคงอยู่ให้ตรวจแก้ กรณีเครือข่ายขัดข้องให้โหลดทะเบียนตรวจผลก่อนลองใหม่ ระบบตรวจคนซ้ำและหมายเลขซ้ำบนเซิร์ฟเวอร์อีกครั้ง

ชื่อและวันเกิดตรงกันจะป้องกันการสร้างซ้ำ ชื่อคล้ายกันหรือไม่มีวันเกิดให้เลือกข้อมูลเดิม หรือระบุเหตุผลเมื่อเป็นคนละคน ข้อมูลที่หน้าจออื่นแก้ไปแล้วจะไม่ถูกเขียนทับ ต้องโหลดข้อมูลใหม่ก่อนบันทึก มีประวัติผู้ทำรายการ ค่าก่อน/หลัง และเหตุผล โดยไม่บันทึกเอกสารส่วนบุคคลลงประวัตินี้

## อัปเดตฐานข้อมูล PostgreSQL / Supabase

ต้องใช้ migration `backend/migrations/postgres/008_team_data_center.sql` ก่อนใช้งานโค้ดชุดนี้ การพัฒนาครั้งนี้ **ไม่ได้รันกับ Supabase จริง**

1. สำรองฐานข้อมูล และทดสอบกับฐานข้อมูลแยกก่อน
2. หยุด backend รุ่นเดิมทุก instance และงานที่อาจเขียนรายชื่ออัตโนมัติ เพื่อไม่ให้เขียนทับรายชื่อแบบเลือกเองระหว่างเปลี่ยนรุ่น
3. ตรวจว่า `backend/.env` ชี้ฐานข้อมูลที่ตั้งใจอัปเดต โดยไม่ส่งรหัสผ่านในแชต
4. ภายใน `backend` เรียก `node scripts/migrateTeamDataCenter.js` เพื่อตรวจสถานะ (ไม่แก้ฐานข้อมูล)
5. เรียก `node scripts/migrateTeamDataCenter.js --apply` เพื่ออัปเดตเฉพาะ 008 ภายใน transaction และบันทึก checksum
6. เปิด backend และ frontend รุ่นใหม่ร่วมกัน ตรวจทีมเดิมว่ายังมีรายชื่อ และทดสอบทีมใหม่เลือก/ยืนยัน รวมถึงคำขออนุมัติ ก่อนเปิดใช้งานทั้งหมด

ห้ามเปิด backend รุ่นเดิมกลับมาเขียนข้อมูลหลัง migration โดยไม่ประเมินการย้อนรุ่น การย้อนกลับควรใช้แผนกู้คืนที่ทดสอบแล้วและคำนึงถึงข้อมูลที่เพิ่มหลังอัปเดต
