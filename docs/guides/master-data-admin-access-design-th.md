# แผนตรวจ Master Data และแยกผู้ดูแล Volley เป็น 3 ส่วน

วันที่ตรวจโค้ด: 16 พฤศจิกายน 2026

สถานะพัฒนาล่าสุด: migration 004 ใช้กับฐาน local แล้ว (29 ตาราง) และทำหน้าจอร่วมของผู้ดูแลทั้ง 3 ส่วนตาม [ผลขั้นตอนที่ 4](../technical/admin-workspaces-step-4-2026-11-16.md) ข้อมูลการตรวจโค้ดและจำนวน 24 ตารางด้านล่างเป็นบันทึกรอบแรก

นโยบายสิทธิ์ฉบับยืนยันอยู่ที่ [ผลตรวจและแบบสิทธิ์ขั้นที่ 2](../technical/access-control-step-2-2026-11-16.md) พร้อมทะเบียน API 170 จุดประกาศ route ใช้เอกสารขั้นที่ 2 เป็นข้อกำหนดในการพัฒนาต่อ

ฐานหลักที่ผู้ใช้ยืนยันล่าสุด: PostgreSQL ในเครื่อง `Volley_db2026` / schema `volley` สร้างจากโครงสร้างต้นทางในเครื่องแล้ว มี 24 ตารางแต่ยังไม่มีแถวข้อมูล ดู [ผลตรวจขั้นที่ 1 ของฐานในเครื่อง](../technical/local-postgres-master-data-2026-11-16.md) จำนวนข้อมูลจาก Supabase ด้านล่างเป็นอีกปลายทางหนึ่ง

อัปเดตภายหลัง: ตรวจยืนยันแล้วว่าเคยย้ายข้อมูลไป Supabase PostgreSQL และอ่านฐานปลายทางจริงสำเร็จ พบ 24 ตาราง รวม 160 แถว ดู [ผลยืนยันฐานข้อมูล](../technical/database-provider-verification-2026-11-16.md) ข้อความเรื่องยังไม่ตรวจข้อมูลจริงด้านล่างอธิบายขอบเขตของการตรวจโค้ดรอบแรก

เอกสารนี้เป็นผลตรวจโครงสร้างโค้ดและข้อเสนอออกแบบ ยังไม่ได้เปลี่ยนสิทธิ์ระบบหรือรัน migration และยังไม่ได้ตรวจแถวข้อมูลในฐานข้อมูลจริง จึงไม่ใช่ข้อยืนยันจำนวนข้อมูลซ้ำ/บัญชีที่ไม่ใช้งาน โครงสร้างอ้างอิง migrations รวมถึง PostgreSQL baseline ซึ่งต้องเทียบกับ schema ที่ติดตั้งจริงก่อนพัฒนา

## 2. Master Data: มีแล้ว ขาดอะไร และอะไรซ้ำ

Master Data คือข้อมูลอ้างอิงและตัวตน ส่วนการลงทะเบียน รายชื่อประจำรายการ คะแนน และสถิติเป็นข้อมูลปฏิบัติงาน ไม่ควรรวมทุกอย่างไว้ในเมนู Master Data

| กลุ่ม | มีในระบบ | ช่องว่าง/แนวทาง |
|---|---|---|
| บัญชีและสิทธิ์ | users, permission map, สถานะบัญชี | หนึ่งบัญชีหนึ่งบทบาท เพิ่มขอบเขตรายการและประวัติการมอบสิทธิ์ |
| ทีม | teams, ชื่อสองภาษา, สี, เอกสาร, ผู้ติดต่อ | แยกสถานะตรวจรับกับสถานะเปิดใช้งาน; ตรวจ code/ชื่อซ้ำก่อนรวม |
| นักกีฬา | players, ตัวตน, วันเกิด, ตำแหน่ง, เอกสาร, integrity constraints | ตรวจตัวตนซ้ำโดยใช้รหัสที่เหมาะสม; ไม่รวมคนจากชื่อเหมือนกันอย่างเดียว |
| บุคลากรทีม | team_staff และ team_entry_staff | role แบบข้อความควรมีรหัสตำแหน่งอ้างอิง; แยกบุคคลกับบัญชี login |
| เจ้าหน้าที่ | referees, scorers, line_judges และ user_id บางประเภท | พิจารณา persons/official_profiles + คุณสมบัติหลายหน้าที่; ไม่บังคับทุกคนมีบัญชี |
| รุ่นอายุ | age_groups และ seed; API อ่าน | ยังไม่เห็น CRUD รุ่นอายุใน routes ที่ตรวจ; เพิ่มกฎอายุ วันตัดอายุ ลำดับ และ active |
| สนาม | stadiums, จำนวนคอร์ต, สถานะ | หากต้องจองรายคอร์ต เพิ่ม courts และตรวจเวลาชน แทน court_number ข้อความอย่างเดียว |
| การแข่งขัน | competitions, เพศ, รุ่นอายุ, กติกาบางส่วน | เป็นข้อมูลจัดงาน; กำหนดเจ้าของรายการและการเผยแพร่แยกจากรับสมัคร open/closed |
| กติกาคะแนน | scoring_config, max_sets และ match_setup | มีฐานแล้ว; เพิ่ม preset/version หากต้องใช้ซ้ำ และเก็บ snapshot ต่อแมตช์ |
| คำศัพท์อ้างอิง | เพศ ตำแหน่ง จังหวัด ประเทศ รหัสสถิติ กระจายใน field/โค้ด | ทำรหัสกลางและคำแปลตามที่ต้องจัดการจริง; ไม่จำเป็นต้องทำทุก enum เป็นตาราง |
| การมอบหมาย | scorer_id, referee IDs, manual_vis_assignee_id, owner | ใช้จัดงาน; ผู้บันทึกแมตช์ทางการเข้าถึงทุกแมตช์ในรายการที่ได้รับสิทธิ์ |

### จุดซ้ำที่ต้องตัดสินตามหน้าที่ของข้อมูล

| จุดที่ดูซ้ำ | ประเภท | ข้อเสนอ |
|---|---|---|
| team_competitions / team_entries | mirror เพื่อ compatibility | ใช้ team_entries เป็นเป้าหมายหลัก ย้ายผู้อ่านเดิมและเทียบผลก่อนเลิก mirror |
| players / team_entry_players / athlete_snapshot | ตัวตนกับรายชื่อและหลักฐาน ณ เวลาลงทะเบียน | เก็บไว้ แยกความหมายให้ชัด ห้ามแก้ประวัติย้อนหลังตามข้อมูลหลักอัตโนมัติ |
| users / scorers / referees | บัญชีกับบุคลากร | เชื่อมด้วย ID และตรวจรายการกำพร้า ไม่ใช่ลบทิ้งเพราะชื่อซ้ำ |
| ชื่อเจ้าหน้าที่ใน matches กับ official IDs | อาจเป็น snapshot/กรอกเอง/ข้อมูลเก่า | ระบุ source และเวลาสำเนา ตรวจ report ก่อนรวม |
| teams.coach / manager_name กับ team_staff | ผู้ติดต่อกับบุคลากรอาจทับกัน | กำหนดเจ้าของข้อมูลและตัวดึงไปแสดง; ตรวจทุกจุดอ่านก่อนลด field |
| home_color/away_color กับ main_color/second_color/third_color | ความหมายอาจต่างตามชุดแข่ง | ทำ mapping ของ UI/รายงานก่อนตัดสินเลิกใช้ |
| address/province กับ address_* | ที่อยู่เต็มกับแยกส่วน | กำหนดแหล่งหลักและสร้างข้อความแสดงผลจากส่วนย่อยเมื่อเหมาะสม |
| ชื่อเดิมกับ name_th/name_en หรือ title_th/title_en | compatibility และ fallback สองภาษา | กำหนด fallback กลาง ตรวจ API/รายงานก่อนลบชื่อเดิม |
| match_events / match_actions / live_state / vis_state | เหตุการณ์คะแนน เหตุการณ์สถิติ และ state | ไม่ใช่ข้อมูลซ้ำที่ลบได้ทันที กำหนดแหล่งจริงและวิธี reconcile แยกตามโดเมน |
| custom_vis_matches / manual scorer matches | แมตช์อิสระคนละ workflow | กำหนดชนิดและเจ้าของ ไม่รวมอัตโนมัติจากชื่อทีม/เวลา |

ยังไม่มี field/table ใดที่ยืนยันว่า “ไม่ใช้งานแล้ว” จากการตรวจครั้งนี้ การไม่พบหน้าแก้ไขไม่เท่ากับไม่มีการใช้งาน

## 3. โครงสร้างผู้ดูแลที่เสนอ

ใช้ชื่อฐานข้อมูลตัวพิมพ์เล็ก: super_admin, super_admin_scorer, super_admin_vims โดยคำว่า Admin หมายถึงส่วนบริหารการแข่งขันทั่วไป และ VIMS หมายถึงผลิตภัณฑ์สถิติที่โค้ดปัจจุบันใช้ชื่อ VIS

| พื้นที่ | ผู้ดูแล | ผู้ปฏิบัติงาน |
|---|---|---|
| ระบบกลางและ Admin | super_admin | organizer, team_staff, referee |
| Scorer | super_admin_scorer | scorer |
| VIMS | super_admin_vims | vims_operator |

super_admin ดูแลบัญชีผู้ดูแลทั้งสองส่วน นโยบายระบบ Master Data กลาง และ audit ทั้งระบบ ผู้ดูแล Scorer/VIMS จัดคน งาน และตรวจรับเฉพาะส่วน ไม่สามารถสร้าง super_admin หรือให้สิทธิ์ข้ามส่วนได้

ผู้ดูแลทุกประเภทบันทึกคะแนนหรือสถิติไม่ได้ หนึ่งบัญชีมีบทบาทเดียว ผู้ดูแล Scorer/VIMS ตรวจรับงานในส่วนของตนและเฉพาะรายการที่ได้รับสิทธิ์ ไม่เพิ่มบทบาทผู้บันทึกให้บัญชีผู้ดูแล

### ตารางสิทธิ์เป้าหมาย

“ตามขอบเขต” หมายถึงรายการที่ได้รับสิทธิ์หรือทีมตน ผู้บันทึกเข้าถึงทุกแมตช์ทางการในรายการนั้นได้ เซิร์ฟเวอร์ต้องตรวจทุก request รวมการอ่านและส่งออก สิทธิ์ถือเครื่อง Offline เป็นข้อจำกัดป้องกันการเขียนชนแยกต่างหาก

| Role | จัดบัญชี/สิทธิ์ | ข้อมูลหลัก/จัดแข่ง | คะแนน | สถิติ | ตรวจรับ/เปิดแก้ | รายงาน |
|---|---|---|---|---|---|---|
| super_admin | ทุกส่วน | ทั้งระบบ | ดู | ดู | จัดการนโยบาย; ไม่ข้ามผู้ตรวจส่วนงานโดยอัตโนมัติ | ทั้งระบบ |
| super_admin_scorer | เฉพาะคน Scorer และรายการที่มีสิทธิ์ | อ่านข้อมูลที่จำเป็น/จัดงาน Scorer | ดู | ดูสรุป | ยืนยัน/ส่งกลับ/เปิดแก้ผลตามรายการที่มีสิทธิ์ | คะแนนตามขอบเขต |
| super_admin_vims | เฉพาะคน VIMS และรายการที่มีสิทธิ์ | อ่านข้อมูลที่จำเป็น/จัดงาน VIMS | ดู | ดู | ยืนยัน/ส่งกลับ/เปิดแก้สถิติตามรายการที่มีสิทธิ์ | สถิติตามขอบเขต |
| organizer | ไม่ให้ role ระบบ | รายการ ทีมลงทะเบียน ตารางสนาม ตามขอบเขต | ดู | ดู | ส่งคำขอแก้ | ตามขอบเขต |
| scorer | แก้โปรไฟล์ตนเอง | อ่าน roster ที่อนุมัติ | ทุกแมตช์ทางการในรายการที่มีสิทธิ์ | ไม่มีสิทธิ์บันทึก | ส่งตรวจผล | ตามขอบเขต |
| vims_operator | แก้โปรไฟล์ตนเอง | อ่าน roster ที่อนุมัติ | อ่าน | ทุกแมตช์ทางการในรายการที่มีสิทธิ์ | ส่งตรวจสถิติ | ตามขอบเขต |
| team_staff | ไม่มี | ทีมตน/รายชื่อ/เอกสารตนก่อนล็อก | ดู/ส่งคำขอตามกติกา | ข้อมูลสาธารณะ | ยืนยันส่งรายชื่อ | เอกสารทีมตน |
| referee | ไม่มี | อ่านงานที่อนุญาต | ดู | ดูที่อนุญาต | ไม่มีในขอบเขตนี้ | ใบงานที่อนุญาต |
| guest | ไม่มีบัญชี | เฉพาะข้อมูลสาธารณะ | ทุกแมตช์ทางการตามเดิม | ข้อมูลสาธารณะตามเดิม | ไม่มี | เฉพาะรายงานสาธารณะ |

เอกสารระบุตัวนักกีฬา/เบอร์ส่วนตัวไม่รวมในสิทธิ์อ่าน roster ทั่วไป ต้องมี athlete.document.read แยก และห้ามออกไปกับรายงานสาธารณะ

### โครงสร้างสิทธิ์ที่ควรเพิ่ม

- roles, permissions, role_permissions: กำหนดความสามารถอย่างชัดเจน ลด wildcard
- users.role เป็นบทบาทเดียว; user_competition_access เก็บ user_id, competition_id, granted_by, granted_at, revoked_at และตรวจสิทธิ์ตามรายการ
- match_assignments หากใช้มีหน้าที่จัดงาน ไม่บังคับเป็น ACL ของแมตช์ทางการ; lease/revision ป้องกันผู้บันทึกเขียนชนกัน
- review_records: domain (score/vims), match_id, revision, decision, reviewer_id, reason, เวลา
- audit_logs เดิม: ใช้ต่อ เพิ่มรายละเอียดก่อน/หลังและ scope เท่าที่จำเป็น โดยไม่เก็บรหัสผ่าน/token/เนื้อหาเอกสารส่วนตัว

ตัวอย่าง permission: system.manage, identity.manage, master.manage, competition.manage, scorer.users.manage, scorer.assign, score.record, score.submit, score.review, score.reopen, vims.users.manage, vims.assign, vims.record, vims.submit, vims.review, vims.reopen, report.export, athlete.document.read

สิทธิ์ที่แท้จริง = บัญชี active + permission + scope + assignment/ownership + สถานะงานที่อนุญาต ตรวจทั้ง HTTP, socket, download และ offline sync การซ่อนเมนูเป็นเพียง UX

ด้านซ้ายเป็นเมนูตาม permission; เนื้อหามีชื่อหน้า ตัวกรอง งานค้าง ตาราง และรายละเอียดด้านข้าง ใช้คำว่า “Scorer” กับ “VIMS” ชัดเจนแทนชื่อ AdminScorer ที่อาจทำให้เข้าใจว่าเป็นผู้ดูแลระบบ

```text
┌ Volley │ พื้นที่: ระบบกลาง ▼ │ รายการ ▼ │ ออนไลน์ │ ผู้ใช้ ┐
│ เมนู             │ ภาพรวมระบบ                              │
│ ภาพรวม           │ [บัญชีรออนุมัติ] [ข้อมูลต้องตรวจ] [งานค้าง] │
│ Master Data      │ ตัวกรอง: รายการ / ประเภทปัญหา / สถานะ    │
│ การแข่งขัน       │ รายการข้อมูล │ ปัญหา │ ผู้รับผิดชอบ │ เปิดดู │
│ ผู้ใช้และสิทธิ์   │                                           │
│ ประวัติ          │ รายละเอียด / ประวัติ / การดำเนินการ       │
└──────────────────┴───────────────────────────────────────────┘
```

| organizer | รายการของฉัน, รับสมัคร, ทีม/รายชื่อ, ตารางสนาม, ความพร้อม | เตรียมรายการ อนุมัติทีม จัดตาราง ตรวจชน |
| scorer | งานวันนี้, แมตช์ของฉัน, ดาวน์โหลด Offline, ประวัติส่งตรวจ | ตรวจ roster → เตรียมแมตช์ → บันทึก → ตรวจทาน → ส่งตรวจ |
| vims_operator | งานของฉัน, แมตช์อิสระที่ได้รับอนุญาต, Offline, ประวัติ | รับงาน → ตรวจ roster/lineup → บันทึก rally → ตรวจครบ → ส่งตรวจ |
| team_staff | ทีมของฉัน, นักกีฬา/บุคลากร, ลงรายการ, ยืนยันรายชื่อ, แมตช์ | อัปโหลดเอกสารของทีม ส่งรายชื่อและคำขอ |
| referee | แมตช์ที่ได้รับมอบหมาย, รายชื่อ, คะแนนสด, ใบรายงาน | อ่าน/รับรองเมื่อได้รับสิทธิ์เฉพาะ |
| guest | Dashboard สาธารณะและรายงานสาธารณะ | ดูแมตช์ทางการตามเดิม |

หน้าคุณภาพข้อมูลต้องมี: ประเภทข้อมูล, ID, ปัญหา, ระดับความมั่นใจ, จำนวนจุดอ้างอิง, ผู้รับผิดชอบ และปุ่มดูรายละเอียด ก่อนรวมข้อมูลให้แสดงแถวต้นทาง/ปลายทาง รายการที่จะเปลี่ยน และผลกระทบต่อรายงาน ห้ามปุ่มลบซ้ำอัตโนมัติจากชื่อ

หน้าผู้ใช้/สิทธิ์ต้องมี: โปรไฟล์, สถานะบัญชีรวม banned, บทบาทเดียว, รายการที่ได้รับสิทธิ์, ผู้มอบสิทธิ์ และประวัติ แสดงคำอธิบายเมื่อปุ่มถูกปิดเพราะ scope หรือสถานะงาน

หน้ารายละเอียดแมตช์แยกแท็บ: ข้อมูลทั่วไป / รายชื่อ / คะแนนทางการ / สถิติ VIMS / การตรวจรับ / ประวัติ แต่ละส่วนแสดงเจ้าของงาน สถานะ revision ผู้แก้ล่าสุด และเวลาซิงค์

## 5. ลำดับการใช้งานตั้งแต่เริ่มต้น

1. super_admin ตั้งค่าข้อมูลอ้างอิง สร้างผู้ดูแล Scorer/VIMS และมอบขอบเขต
2. organizer สร้างรายการ เลือกกติกา สนาม รุ่นอายุ/เพศ และช่วงรับสมัคร
3. team_staff จัดข้อมูลทีม นักกีฬา เอกสาร และสมัครรายการ
4. organizer ตรวจคุณสมบัติ อนุมัติรายการลงทะเบียน ตรวจและล็อกรายชื่อ
5. organizer จัดคู่แข่ง ตารางและคอร์ต ตรวจทีม/สนาม/บุคลากรเวลาชน
6. ผู้ดูแล Scorer/VIMS ให้สิทธิ์รายการแก่ผู้บันทึกในส่วนของตน การจัดคนรายแมตช์เป็นงานตาราง ไม่เป็นข้อจำกัดสิทธิ์เข้าถึงทุกแมตช์ทางการในรายการนั้น
7. scorer ตรวจรายชื่อและความพร้อม บันทึกคะแนนทางการ; vims_operator บันทึกสถิติในพื้นที่ของตน โดยไม่เขียนทับผลทางการ
8. ผู้บันทึกส่งตรวจแยกสองส่วน แมตช์สร้างเองต้องผูกรายการก่อนส่ง; ผู้ดูแล Scorer ยืนยันคะแนน ผู้ดูแล VIMS ยืนยันสถิติหรือส่งกลับพร้อมเหตุผล
9. แมตช์ทางการยังเปิดดูคะแนนสด รายชื่อ และใบบันทึกผลตามเดิม รายงานระบุ revision และสถานะรับรองแยกจากการมองเห็นสาธารณะ แมตช์อิสระคงข้อจำกัดส่วนตัวเดิม
10. หากต้องแก้ข้อมูลที่รับรองแล้ว ให้ยื่นคำขอ ผู้มีสิทธิ์เปิดแก้พร้อมเหตุผล สร้าง revision ใหม่ ตรวจรับใหม่ และคำนวณผลกระทบต่ออันดับ/รายงาน

สถานะเป้าหมายแยกกัน: แมตช์ draft → ready → live → completed (มี cancelled); ผลและสถิติแต่ละส่วน draft → submitted → confirmed หรือ returned → submitted ใหม่; การเปิดแก้ confirmed → reopened → submitted; การเผยแพร่เป็นสถานะแยก การซิงค์เป็นอีกมิติหนึ่ง ไม่ใช้คำว่า completed แทน confirmed/published

Offline: ออก grant ตาม domain/แมตช์/ผู้ใช้/อายุสิทธิ์และ revision ใช้ idempotency key เมื่อซิงค์ ตรวจสิทธิ์ปัจจุบันและ version อีกครั้ง เมื่อสิทธิ์ถูกถอนแต่ยังออฟไลน์อาจใช้งาน cache ได้จน grant หมดอายุ จึงต้องแสดงข้อจำกัดนี้และกักงานขัดแย้งไว้ตรวจ ไม่ทิ้งข้อมูลบันทึกหรือรับเข้าโดยอัตโนมัติ

## 6. งานตรวจข้อมูลจริงก่อนสรุปว่าขาด/เกิน/ไม่ใช้

ทำด้วยบัญชีอ่านอย่างเดียวและรายงานเฉพาะ ID/จำนวน ไม่ส่งข้อมูลส่วนตัวออกมาโดยไม่จำเป็น

| การตรวจ | เกณฑ์และผลที่ต้องได้ |
|---|---|
| Schema จริง | provider, migration ที่ใช้แล้ว, columns/index/FK เทียบ baseline |
| จำนวนข้อมูล | count ตามตาราง สถานะ รายการ และชนิดแมตช์ แยก sandbox/ข้อมูลจริง |
| ความสัมพันธ์ | FK กำพร้า user↔official/team, entry↔player, match↔team/competition |
| ข้อมูลซ้ำ | team code, ตัวตนนักกีฬา, official user link, entry ตามรายการ/รุ่น/เพศ; แยกซ้ำแน่นอนกับสงสัย |
| ข้อมูลไม่ครบ | วันเกิด/รุ่นอายุ เอกสารที่รายการบังคับ สนาม ผู้รับงาน รายชื่อก่อนเริ่ม |
| Mirror | เทียบ team_entries กับ team_competitions ตาม key ที่แต่ละตารางรองรับ รวม status ไม่ตรง |
| สิทธิ์เดิม | จำนวนบัญชีต่อ raw role และ normalized role, status approved ที่ยังเหลือ, role ที่ไม่มี permission |
| ข้อมูลอาจไม่ใช้ | ตรวจ reference ทั้งโค้ด API รายงาน script งานภายนอก และ audit; ไม่มี reference/แถวไม่พอสรุปลบ |
| คะแนน/สถิติ | ตรวจความสอดคล้องเฉพาะข้อมูลชนิดเดียวกัน; VIMS ที่บันทึกไม่ครบไม่ใช่เหตุแก้คะแนนทางการ |

ผลลัพธ์ควรเป็นทะเบียนปัญหา: issue_id, entity_type, entity_id, rule, severity, evidence, proposed_action, owner, status พร้อมยอดก่อน/หลังแก้และหลักฐานย้อนกลับ

## 7. แผนพัฒนาและย้ายสิทธิ์ทีละขั้น

| ระยะ | งาน | เกณฑ์ตรวจรับ |
|---|---|---|
| 1 ตรวจจริง | inventory และรายงานคุณภาพข้อมูลแบบอ่านอย่างเดียว | มีจำนวนและตัวอย่าง ID ของปัญหา ไม่ด่วนลบข้อมูล |
| 2 ออกแบบสิทธิ์ | permission registry, scope, assignment, role mapping | ระบุทุก API/หน้า/socket/offline ว่าใช้ permission และ scope ใด |
| 3 ย้ายบัญชี | เพิ่มโครงสร้างและ migration ย้อนกลับได้; เทียบสิทธิ์เก่า/ใหม่ | admin → super_admin; score/scorer → scorer; statistician ต้องตรวจหน้าที่จริงก่อนเป็น vims_operator; organizer คงบทบาทเดิมและเพิ่มขอบเขตรายการ; staff/user ต้องทบทวนรายบัญชี |
| 4 ทำหน้าจอ | app shell และ Dashboard ทั้ง 3 พื้นที่ ต่อด้วยตารางและรายละเอียด | ผู้ใช้เห็นเฉพาะพื้นที่ที่มีสิทธิ์ การเปิดลิงก์ตรงให้ผลตรง API |
| 5 แยกการบันทึก | score.record กับ vims.record, scope และ assignment | Scorer เขียน VIMS ไม่ได้ และ VIMS เขียนคะแนนทางการไม่ได้ รวม Offline |
| 6 ตรวจรับ/เผยแพร่ | revision, reviewer, reopen, publication, audit | ทดสอบส่งกลับ แก้ใหม่ ไม่ตรวจตนเอง และรายงาน revision ตรงกัน |
| 7 ลดความซ้ำ | ย้ายผู้อ่าน mirror ทีละกลุ่ม ยกเลิก field เมื่อไม่มี dependency | เทียบ fixture/roster/standings/reports ก่อนหลัง และมี rollback |

จุดแก้หลัก: backend/config/permissions.js, middleware/authMiddleware.js, controllers/authController.js, routes ทุกชุด, การตรวจ socket ใน server, client/src/App.jsx, login/entry routing, หน้า Admin/Scorer/VIS, offline grant/checkout/sync และชุดทดสอบเดิม

ก่อนใช้งานจริงต้องทดสอบอย่างน้อย: บัญชี inactive/banned, ข้ามรายการ, ข้ามทีม, เข้าลิงก์ตรง, เรียก API เอง, role ถูกถอนระหว่าง session, lease ชน, แก้หลังรับรอง, ผู้ตรวจงานตนเอง, sync ข้อมูลเก่า, export เอกสารส่วนตัว และการบังคับหนึ่งบัญชีหนึ่งบทบาท

สำหรับการพัฒนาต่อให้รัน lint/build ฝั่ง client และชุดทดสอบ backend ที่เกี่ยวข้อง โดยเฉพาะ recording-policy, permissions, authTokenSelection, manualVisAccess และ Offline routing ไม่ควรเปลี่ยน alias statistician ก่อนทำแผนย้ายบัญชีและตรวจ endpoint ครบ
